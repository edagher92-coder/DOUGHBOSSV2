# DoughBoss 2.46.0 — Square catering, decline handling, loyalty accrual (Claude)

## 15 Oct 2026 — Claude (Cowork), branch `square-fullstack` from `codex/live-2.45.0`

Status: **committed locally, not pushed, not deployed.** Codex: please review, push, tag and own any merge. DB version unchanged (1.29.0); no schema changes.

### What changed

1. **Card declines no longer strand the cart** (`class-doughboss-square.php`, `class-doughboss-payment-attempts.php`).
   - `request()` errors now carry `square_http`, `square_category` and `square_code`.
   - `is_payment_method_refusal()` = `doughboss_pay_api` + `PAYMENT_METHOD_ERROR` + HTTP 400 or 402.
   - On a refusal from `POST /v2/payments`, the attempt goes `dispatching|processing` to `failed` via `mark_irreversible_failed()`, but only while `provider_reference IS NULL`. The response is 402 with `payment_pending=false` and `retry_safe=true`.
   - A storefront CreateOrder API failure is treated the same way. `approved_preorder` keeps the old held behaviour.
   - 5xx, timeouts and unknown errors still go to `unknown` (money may have moved).
2. **Retry-safe pre-dispatch errors** (`class-doughboss-rest-controller.php`).
   - The public `create_payment_intent()` wraps the now-private `create_payment_intent_inner()`.
   - Any `WP_Error` returned before Square or the payment gateway is dispatched gets `payment_pending=false` and `retry_safe=true`.
3. **Catering via Square invoices** (new `class-doughboss-square-invoices.php`).
   - Route: `POST /admin/catering/{id}/square-invoice {leg}`, behind `verify_manage`.
   - Steps: customer search or create, then `/v2/orders` (total verified), then `/v2/invoices` (EMAIL, card only, BALANCE request), then the intent is stored as `sqinv:<invoice_id>`, then publish.
   - Resends resume the stored intent, never duplicate. The quote lock is held throughout.
   - The webhook `invoice.*` branch uses `claim_event`/`complete_event`, then `reconcile()`. `reconcile()` GETs the invoice and calls `mark_paid` only if the status is PAID, the location matches, and the computed amount and AUD completed amount are at least the leg amount. `retry` returns 500.
   - New `commerce_request()` is allow-listed to `/v2/customers|orders|invoices|loyalty` and requires `square_shop_ready`.
   - Admin buttons were added in the Catering list.
4. **Catering notice.**
   - `catering_min_notice_business_days` defaults to 2 and is clamped to 0–30. Weekends are skipped.
   - Enforced in `DoughBoss_Catering::create()` (error `doughboss_catering_notice`, 400, `earliest_date`).
   - The form shows a `min` date and a hint (`data-notice-days`). The setting is in Settings > Catering.
   - Public holidays are NOT excluded. [CONFIRM with Elie]
5. **Catering payment receipts** (new `class-doughboss-catering-emails.php`, hooked on `doughboss_catering_payment`). Sends once per enquiry and leg, using an `add_option` guard. The existing enquiry-received emails are unchanged apart from copy that mentions the Square payment link.
6. **`buyer_email_address`** is added to `POST /v2/payments`. It is read only from the hash-verified checkout snapshot, and only for orders protocol 1.
   - Edge case: an attempt prepared on 2.45.0 and dispatched after the upgrade would send a different body under the same idempotency key. Upgrade with ordering paused.
7. **Square Loyalty accrual** (new `class-doughboss-square-loyalty.php`).
   - A wp-cron job runs 20s after `doughboss_order_created` for Square-paid orders.
   - Steps: get program `main` (cached), search the loyalty account by E.164 phone, then accumulate with `order_id` and a deterministic key.
   - It never enrols anyone. It is a no-op without an ACTIVE program. Retries up to 4 times with backoff. Toggle: `square_loyalty_accrual` (default on).
8. Version 2.46.0 and readme changelog.
