### What changed and why

The owner wants Square's own hosted checkout page as the forward model for all stores. It is built behind a setting so the shipped embedded flow stays the default until sandbox testing passes.

1. **Setting** `square_checkout_style` (`embedded` or `hosted`).
   - Accessor: `DoughBoss_Settings::square_checkout_style()`.
   - Admin: Settings > Square > "Checkout style" radio.
   - The sanitizer only changes the value when `square_checkout_style_present` is posted (the `square_wallets_present` pattern). Any value other than `hosted` saves as `embedded`.
2. **New `includes/class-doughboss-square-hosted.php`.**
   - Pure helpers:
     - `payment_link_body()`, `link_facts()`.
     - `return_url()`, `same_site_https()`, `returned_checkout_key()`.
     - `checkout_url_valid()` (Square hosts per mode).
     - `au_e164()`.
     - `order_payment_state()`.
     - `paid_proof()`.
   - Orchestration: `create_checkout()`, `confirm()`, `retire_unpaid()`, `stale_attempts()`, `attempt_for_event()`.
   - A 15-minute WP-Cron sweep (`doughboss_square_hosted_sweep`) is booked while the gateway is Square. It is cleared on deactivate and uninstall.
3. **Narrow transport.** `DoughBoss_Square::online_checkout_request()` allows exactly four calls through an attempt-validated shop binding:
   - `POST /v2/online-checkout/payment-links`
   - `DELETE /v2/online-checkout/payment-links/{id}`
   - `GET /v2/orders/{id}`
   - `GET /v2/payments/{id}`

   `commerce_request()` is not widened. New public wrappers: `attempt_binding()` and `attempt_projection()`.
4. **`/payment-intent` (gateway `square` + hosted).**
   - Same contact validation, voucher reservation and immutable checkout snapshot as embedded. It reuses the same `square-v2` attempt identity, cart guard, binding hash and `square-orders-v1` projection.
   - The attempt is created, then claimed (`dispatching`, with the voucher claimed through `claim_payment_dispatch`).
   - Square is sent `CreatePaymentLink` with:
     - `order` = the same itemised, location-bound projection (Square owns `state`).
     - `idempotency_key` = `idempotency_key('plink', checkout_key)`.
     - `checkout_options`: `redirect_url` (same-site HTTPS + `?doughboss_square_return=<checkout_key>`), `ask_for_shipping_address:false`, `accepted_payment_methods` {apple_pay, google_pay true; cash_app_pay, afterpay_clearpay false}, `allow_tipping:false`, `enable_coupon:false`, `enable_loyalty:false`.
     - `pre_populated_data` {buyer_email, buyer_phone_number in AU E.164}.
     - `payment_note` = "DoughBoss web order db-attempt-N".
   - The created DRAFT Order is re-read and must match the retained economics, or the link is deleted.
   - The Square Order id is then bound with `bind_square_order()`. The link id and URL are stored in attempt metadata **before** the URL is returned.
   - Response: `{gateway:'square', hosted:true, state:'redirect'|'confirm', checkout_url, checkout_reference}`.
   - A replay with the same attempt key returns the stored link, with no second POST.
   - A new attempt key for the same cart first retires an unpaid earlier link (DELETE, then re-read the Order as CANCELED). It never retires a tendered Order.
5. **Browser return: `/checkout` with `square_checkout=<checkout_key>`.**
   - The attempt must be hosted, ordinary (web or table_qr), and owned by this cart session (cart guard).
   - `confirm()` does `GET /v2/orders/{bound id}`. Order state is never used as payment proof. The Order must have exactly one tender, then `GET /v2/payments/{tender payment_id}`.
   - `paid_proof()` (via `DoughBoss_Square_Orders::validate_hosted_response()`) requires all of:
     - Payment `COMPLETED` with `source_type CARD` (card brand not `SQUARE_GIFT_CARD`; `card_details.status` `CAPTURED` when present).
     - Exact amount and currency, zero tip, and `total_money` equal to the amount.
     - Payment `order_id` equal to the bound Order, and Payment location equal to the bound location.
     - Order id, location and `db-attempt-N` reference all match.
     - Order state OPEN or COMPLETED, one CARD tender for that payment and amount, `net_amount_due` 0.
     - Unchanged line items, taxes and discounts. At most one money-free DIGITAL fulfillment (which Square adds). No refunds, returns, rewards or service charges.
   - Proven: `bind_irreversible_reference(..., 'succeeded', 'COMPLETED')`, then `reconcile_irreversible_reference()` (sets `verified_at`), then `finalize_square_hosted_order()`.
   - Unproven COMPLETED payment: bound as `mismatch` and held for staff. No order, no retry.
6. **`finalize_square_hosted_order()`** mirrors Stripe `recover_stripe_order()`/`finalize_stripe_order()`:
   - It is the only order writer for browser, webhook and sweep.
   - It uses only the hash-verified snapshot (items, contacts, money) and the voucher redeem idempotency `order_<checkout_key>`.
   - `DoughBoss_Order::create()` unique keys make races replay a single order and a single confirmation. After that it completes the snapshot, sets the attempt to `order_committed` and links the voucher.
   - A policy change to staff approval while the customer is on Square sets `reconciliation_hold` and records the payment as unreconciled. It never auto-fulfils.
7. **Webhook.** `payment.*` (data.type `payment`) and `order.updated` (data.type `order_updated`) are resolved to a hosted attempt by payment id or bound Order id. Payload values are lookup hints only.
   - Each event is handled once through `claim_event`/`complete_event` and goes through the same settle path.
   - Terminal holds are recorded as unreconciled. Transient failures return 500, so Square retries.
   - Embedded payments are untouched: `attempt_for_event()` ignores non-hosted attempts.
8. **Abandoned checkout.** The sweep takes hosted `dispatching` attempts older than 45 minutes plus 15 minutes of grace, matching the voucher `RESERVATION_TTL_SECONDS` of 2700 and the browser resume window.
   - Paid: fulfilled.
   - Unpaid: link deleted, Order confirmed CANCELED with no tender, `mark_irreversible_failed`, then `release_payment_reservation` for the voucher.
   - Uncertain: rotated (`last_error=square_hosted_sweep_retry`) so it cannot starve other rows.
9. **Storefront JS (`public/js/doughboss.js`).**
   - New flag: `squareHosted = PAY.enabled && gateway square && PAY.squareHosted`.
   - Shows a "Secure checkout powered by Square" notice and no card fields. The Web Payments SDK is not enqueued.
   - `doughboss-square.js` keeps ordinary fields dormant (`PAY.squareHosted !== true`).
   - Submit: POST `/payment-intent`, check the Square host for the mode, save the non-card details in `sessionStorage` (`doughbossSquareHostedPending`, 45-minute window), then `window.location.assign(checkout_url)`.
   - Return (`?doughboss_square_return=`, also tolerated with Square-appended params), or coming back to the page: POST `/checkout` with `square_checkout` only. Polling is bounded: 5 reads over about 18 seconds on return, and 1 read on a plain revisit. It only retries "pending/unpaid" answers.
   - Unpaid: "Return to the secure Square checkout" (same link) plus "Change my order instead". The second option starts a new attempt key; the server retires the old unpaid link first.
   - Closed or failed: new attempt key. Anything uncertain: locked with a "do not pay again" message.
   - `request()` errors now carry `code` and `data`, which is additive.
10. **Square Orders validator.** New `validate_hosted_response()`. The embedded `validate_unpaid_response()` and `validate_paid_response()` behaviour is unchanged.
11. **`retrieve_payment_intent()` guard.** It refuses (409, payment pending) hosted attempts, so the embedded path can never quarantine a hosted payment as a mismatch.

### NOT verified / open risks

- **No real Square call was made.** All Square responses were mocked from the documentation. Real sandbox acceptance is required before switching any store to `hosted`.
- **Unverified Square facts:**
  - Whether Square accepts our `order` with `pricing_options`, `reference_id` and ad-hoc taxes and discounts inside CreatePaymentLink.
  - Whether link Orders always carry exactly one DIGITAL fulfillment.
  - Whether the hosted Payment has `source_type CARD` for Apple Pay and Google Pay.
  - Whether Square's checkout might offer a gift card.

  Anything else is held for staff, never auto-paid.
- **Sandbox redirect is incomplete.** Per the Square forum, the customer may not be sent back automatically in sandbox. The page also resumes from `sessionStorage` when the customer navigates back.
- **Lost `sessionStorage` and a different browser.** The return is refused as "unmatched" because of the cart guard. The webhook or sweep still creates the order and the confirmation email.
- **Sweep timing.** It relies on WP-Cron (traffic-driven). A real cron hitting `wp-cron.php` is recommended.
- **Voucher hold.** For an abandoned hosted checkout, the voucher stays held for up to about 75 minutes, or until "Change my order instead".
- **Not browser-tested.** The storefront JS is verified by unit and source tests only.

### Exact sandbox test steps (Elie / Codex)

1. Square Developer Console (Sandbox) webhook subscription must include `payment.updated` and `order.updated` (plus the existing events).
2. On a staging site with 2.47.0, set Settings > Square:
   - Mode: Test, with sandbox credentials and the Revesby sandbox location map.
   - Checkout style: **Square-hosted checkout page**.
   - Then save.
3. Storefront: add 2 items (and, separately, test with a voucher). Enter details and press "Continue … ". The browser must open `https://sandbox.square.link/...`. Check that the Square page shows the same line items and total, with no tip, coupon or shipping.
4. Pay with a Square sandbox test card (from Square's Sandbox payments docs). If Square does not redirect, go back to the shop page in the same tab. It should show "Checking your Square payment…" and then the order number. If not, press **Check my Square payment**.
5. Check the following:
   - Exactly 1 WP order: paid, method square, `payment_intent_id` = the Square payment id.
   - Attempt `order_committed`.
   - Snapshot `completed`.
   - Kitchen board shows the order once and one confirmation email was sent.
   - Square Dashboard shows the Order with note `DoughBoss web order db-attempt-N`.
6. Webhook-only path: start a checkout, pay on Square, then **close the tab without returning**. Within about 1 minute the `payment.updated`/`order.updated` webhook should create the order. Check `doughboss_payment_events` shows `processed`.
7. Abandoned path: start a checkout and do not pay. After at least 60 minutes and the next cron run, check:
   - The attempt is `failed` with `square_hosted_expired`.
   - The link is gone and the Square Order is CANCELED.
   - The voucher can be used again.
8. Back-button path: start, return without paying, then press "Change my order instead". Edit the cart and pay. The old link must be deleted (Square shows its Order CANCELED) and only the new payment creates an order.
9. Apple Pay / Google Pay (sandbox Google Pay where available): confirm the order is created. If it is held as `mismatch`, capture the payment JSON `source_type`. [CONFIRM: Apple Pay/Google Pay source_type]
10. Switch back to **Embedded** and confirm the existing card form still pays normally.
11. Only then set Checkout style = hosted on live (after the `square_live_approved` gate).
