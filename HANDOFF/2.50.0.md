## Design (Square best practice)

| Topic | What 2.50 does | Square doc |
|---|---|---|
| Flow | OAuth **code flow**: a confidential server app holding the application secret. Code-flow refresh tokens don't expire. | [OAuth overview](https://developer.squareup.com/docs/oauth-api/overview) |
| Authorize | `GET /oauth2/authorize` with `client_id`, a space-separated `scope`, and a signed `state`. Production also gets `session=false`, which has no effect in the Sandbox. | [Authorize](https://developer.squareup.com/reference/square/oauth-api/authorize) |
| Token | `POST /oauth2/token`: `authorization_code`, then `refresh_token`. Refresh runs every 7 days or less, and the owner is warned after 8 days without one. | [Refresh/revoke](https://developer.squareup.com/docs/oauth-api/refresh-revoke-limit-scope), [Manage tokens](https://developer.squareup.com/docs/oauth-api/receive-and-manage-tokens) |
| Revoke | `POST /oauth2/revoke` with `Authorization: Client <secret>`, revoking by `merchant_id` | same |
| Storage | Tokens sit in a non-autoloaded option and are never echoed or logged. They are encrypted (libsodium) when `DOUGHBOSS_SQUARE_TOKEN_KEY` is set. The application secret is read env-first. | [Best practices](https://developer.squareup.com/docs/oauth-api/best-practices) |
| Webhooks | Subscriptions belong to the application, not to a seller. There is one subscription; events are routed by the top-level `merchant_id`. | [Webhook subscriptions](https://developer.squareup.com/docs/webhooks/webhook-subscriptions-api), [oauth.authorization.revoked](https://developer.squareup.com/reference/square/oauth-api/webhooks/oauth.authorization.revoked) |
| Catalogue | `BatchUpsertCatalogObjects` with `#` temporary ids. Limits: 1,000 objects per batch and 10,000 per request. Batches are atomic. | [BatchUpsert](https://developer.squareup.com/reference/square/catalog-api/batch-upsert-catalog-objects) |

- **Scopes requested:** PAYMENTS_WRITE/READ, ORDERS_WRITE/READ, CUSTOMERS_WRITE/READ, INVOICES_WRITE/READ, LOYALTY_READ/WRITE, ITEMS_READ/WRITE, SUBSCRIPTIONS_READ, MERCHANT_PROFILE_READ.
- **One application ID for all sellers.** The Web Payments SDK and hosted checkout use the shop's own location ID with that application ID. This is correct for OAuth apps.

## What changed

### New files

**`includes/class-doughboss-square-oauth.php`** handles connections, tokens, refresh and revocation, and webhook routing.

- **State.** The state is `base64url(payload).HMAC` over shop, mode, user, expiry (15 min) and nonce.
  - The nonce is also kept in a transient and is consumed on first use.
- **Callback.** Callback route: `GET /wp-json/doughboss/v1/square-oauth/callback`.
  - REST cookie authentication can't identify the owner on Square's redirect.
  - So the route only shape-checks the parameters and 302s to `wp-admin/admin-post.php?action=doughboss_square_oauth_finish`.
  - That page checks the logged-in owner (`manage_options`), the state's user and mode, and the nonce, then exchanges the code.
- **Connect-time checks.**
  - **Duplicate guard.** One Square account can't serve two shops. Connecting the Revesby account to Bankstown by mistake is refused, and the just-issued token is revoked.
  - **Revesby's merchant is detected automatically.** Its merchant ID is read from the settings token (`GET /v2/locations`).
- **Per shop and mode, the plugin stores:**
  - `merchant_id`
  - access and refresh tokens
  - `expires_at`
  - granted `scopes` (from `/oauth2/token/status`)
  - `location_id`, picked from that account's ACTIVE AUD locations
  - status, timestamps and failures
- **Cron `doughboss_square_oauth_refresh`** (twice daily) refreshes when a token has 23 days or less left, or every 7 days. Failures back off.
- **On-demand refresh** happens inside a request when a token is within 1 day of expiry.
- **Losing access.** A refresh refused as revoked or unauthorized, or an `oauth.authorization.revoked` webhook, wipes the tokens. The shop then reverts to the legacy settings and an admin notice is shown.

**`includes/class-doughboss-square-catalog-copy.php`** copies the Revesby menu to another shop.

- The preview is a dry run and is never stored. Apply rebuilds the plan and must match the previewed hash.
- Phase 1: categories, then modifier lists with their modifiers. Phase 2: items with their variations, pointing at the real IDs from phase 1.
- The ID map is kept in `doughboss_square_catalog_copy_map`. A re-run adds only what is missing; it never updates or deletes anything in the target.
- Not copied:
  - images
  - item options
  - per-location overrides
  - custom attributes
  - inventory
  - TAX objects (taxes are mapped to the target account's tax with the same name and percentage)
- Gift-card and other non-food item types are skipped.

**`admin/class-doughboss-square-accounts-admin.php`** adds the page DoughBoss › Square accounts (owner only).

### Changed

**`DoughBoss_Square`**

- `shop_binding()` adds `merchant_id` only for OAuth-connected shops.
- `access_token($binding)`, `request()` and `mapped_binding_current()` use the shop's own seller token. A bound `merchant_id` must still match.
- The legacy (`null` binding) calls still use the settings token: `test_connection` and the 2.4x locations/catalogue observation and preparation tools.
- The before/after "same context" checks now compare a seller fingerprint, so a token refresh doesn't trip them. Affected: refund, split recovery, gift card, and the catalogue observations.
- New narrow transport `catalog_copy_request()`.
- `orphan_payment()` accepts the routed shop's binding.

**`DoughBoss_Settings`**

- `square_shop_location_id()` reads the effective map: a connection's location wins. A connection with no location picked means "not ready". It never inherits the settings row.
- `square_shop_ready()` checks the shop's own credential.

**Webhook (`square_webhook`)**

- `oauth.authorization.revoked` disconnects that merchant's shops.
- Events are routed by `merchant_id`:
  - a connected shop: processed;
  - Revesby's settings merchant: the 2.49 path;
  - unknown or disconnected merchants: 200, ignored.
- Club subscription events are processed only from the home shop's seller.
- Signature verification is unchanged (app-level key).

**Other**

- The settings page gets a note.
- Uninstall removes the new options. Deactivation clears the cron.

### Coverage

- Every attempt, refund, dispute, invoice, loyalty, tier, gift-card and hosted-checkout call goes through a binding. All of them now use per-shop credentials.

  - the Revesby call carried the settings token.

## Owner steps (in this order)

### 1. Square Developer Console, signed in to the Revesby developer account

1. Open the DoughBoss application, then **OAuth**.
2. **Sandbox** toggle: set Redirect URL to exactly `https://doughboss.com.au/wp-json/doughboss/v1/square-oauth/callback`. The admin page shows the exact string this site computes; use that one if it differs.
3. **Production** toggle: set the same Redirect URL.
4. Copy the **Application secret** for each environment. Preferably add it to `wp-config.php`:
   ```php
   define( 'DOUGHBOSS_SQUARE_TEST_APP_SECRET', '...' );
   define( 'DOUGHBOSS_SQUARE_LIVE_APP_SECRET', '...' );
   define( 'DOUGHBOSS_SQUARE_TOKEN_KEY', '<64+ random chars>' ); // BEFORE connecting; changing it later means reconnecting
   ```
   Alternatively, paste it on DoughBoss › Square accounts. The field is write-only.
5. **Webhooks:** keep the ONE existing subscription (same URL and signature key) and add the event **`oauth.authorization.revoked`**.
   - Sandbox and production each have their own subscription. Add the event to both.

### 2. WordPress

6. Install `doughboss-2.50.0.zip`. Revesby keeps working unchanged.
7. Go to DoughBoss › Square accounts and click **Detect from settings token**. This records Revesby's merchant so stray webhooks are ignored.
8. For **Bankstown**:
   1. Sign out of squareup.com, or open a private window and log into WordPress there.
   2. Click **Connect Square account**.
   3. Sign in with **Bankstown's** Square email and allow access.
   4. Back on the page, pick Bankstown's location and click **Use this location**.
9. Repeat step 8 for **Roselands** with its own email.
10. Leave Bankstown and Roselands **blank** in Settings › Payments › shop mapping. Revesby can stay on settings; connecting Revesby by OAuth is optional.
11. Optional: run **Preview: copy Revesby menu here** for each shop, read the warnings, then **Copy now**. Then add photos in each shop's Square Dashboard.

### Sandbox first

- In the Sandbox, a "shop" is a **sandbox seller test account** in the Revesby developer account. It is not the real Bankstown or Roselands login.
- Create two test accounts and untick "Automatically create authorizations".
- Before clicking Connect, open that account via **Open in Square Dashboard** and keep the tab open. Square requires this in the Sandbox.
- Switch to Live, then redo step 1.3 and steps 7 to 10 with the real accounts.

### When to connect

Connect outside trading hours.

- A shop's binding changes when it connects. That includes Revesby if it is moved to OAuth.
- Payments started a moment before the switch fail closed. The customer sees "contact the shop".

## Not done / limits

- **Apple Pay for Bankstown and Roselands.** Square's RegisterDomain endpoint (`POST /v2/apple-pay/domains`) is meant to be called per seller. That call is not implemented. Cards, Google Pay and hosted checkout are unaffected.
- **The 2.4x catalogue import tools stay single-account (settings token).** These are the website→Square preparation, review and locations observation. For a connected shop they fail closed.
- **Hosted checkout and loyalty caches per shop.** The loyalty program and Club group caches are cleared on connect and disconnect.
- **The Club stays in the home shop's account.** That is Revesby, through `billing_location`.
- **Catalogue copy limits.** It doesn't update objects already copied, doesn't copy images, and doesn't sync the menu continuously.
- **Not verified against real Square.** Nothing was checked there, including the token-status scopes, the revoke response and the `/v2/catalog/list` sizes. Do one complete sandbox connect → pay → refund → webhook → revoke cycle before going live.
