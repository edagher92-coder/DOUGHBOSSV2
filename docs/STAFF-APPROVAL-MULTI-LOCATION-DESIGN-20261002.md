# DoughBoss approval-first multi-location checkout - design candidate

Status: implementation design only; not implemented, activated, published or release-approved.
Source baseline: `00d50b7427cd37fe83bfc6f4ca1314dd78e88268`.

## Outcome and boundaries

Extend the owner's existing online-order requirement that the configured named staff approver confirms a request before payment or kitchen work to pickup requests at Revesby, Bankstown and Roselands. Reuse the durable request/approval/approved-payment lifecycle. Never restore an ordinary direct-pay multi-shop path around approval. Square-owned in-store POS/attendance is not changed. Preserve the unannounced location's privacy and existing voucher history.

No ordering/payment activation, provider mutation, gift-card issuance, split tender, PayOrder, new dependencies, customer-data fixture, deployment, backup upload or credential transfer is included. The configured WordPress approver must be verified; a display name is not an identity. SMS delivery is not claimed without separately configured and proven transport.

## Confirmed current implementation

- `/preorder-request` accepts unpaid requests only while ordinary ordering is closed and after-hours requests are enabled (`DoughBoss_REST_Controller::preorder_request`). Its resolver permits Revesby only.
- Ordinary `/payment-intent` is an independent direct-payment path when ordinary ordering is open. Staff approval is not a global prerequisite there.
- Approved links already have a durable immutable request location, an exact mapped Square context, approved-snapshot binding and server Payment/Order verification before exactly one kitchen release.
- Ordinary multi-shop Square browser bootstrap is intentionally disabled. Approved-link mapping supports the three named public shops locally; this is not live merchant/POS proof.
- Full-value Square Gift Card tender exists, uses Square's hosted input and requires one exact captured tender. Split tender remains disabled by owner decision.

## Required policy and implementation seams

1. Add an explicit server-owned staff-approval-required policy. Missing, unreadable or malformed policy is never permission for direct checkout: missing defaults to approval required; unreadable/malformed configuration denies new intake/payment until repaired. Legacy direct checkout requires a deliberate, valid stored administrator choice. Missing form fields cannot silently save that exception. Do not silently change the meaning of the existing after-hours switch. This default is a consequential change: preserve legacy-positive tests by explicitly configuring their compatibility mode, and add fresh-install/missing-policy negative tests rather than deleting or weakening any assertion.
2. Keep ordinary ordering OFF and after-hours requests OFF throughout implementation and publication. New request availability is server-derived: approved-policy normal-hours request mode must be explicitly opened, or the existing after-hours mode must be explicitly enabled. Master OFF must not be interpreted as permission to create normal-hours requests.
3. Validate the exact configured WordPress user ID, that user's current existence, and existing approval capability server-side. If the required approval actor is not configured or valid, the new mode is unavailable before a request is durably accepted. Decision routes require that same authenticated ID plus capability; any other capable user is denied. Recheck current actor/policy before durable request/decision acceptance. Never auto-create an account, match a person by display name, or fall back to a different staff identity.
4. In the new mode, resolve the submitted native location server-side against the exact supported public-shop set, persisted active state and pickup permission. With multiple active shops, require one exact canonical numeric native ID, not a coercible value or ambiguous alias. The client supplies a preference, never authority. Do not guess a branch, expose an unannounced shop, or accept a browser Square tuple as authority. Square merchant/location readiness is required before approved payment, not falsely treated as proof of open hours or kitchen capacity. An unpaid request does not reserve capacity or promise a collection time. Preserve the existing supported pickup-only semantics; delivery is not added in this slice.
5. Save the location and approved economics through the existing request/snapshot boundary. After request creation, a branch change requires cancellation and a new request; it cannot retarget the existing request, payment attempt or receipt. Approval records retain the exact actor and timestamp.
6. In approval-required mode, ordinary `/payment-intent` and ordinary `/checkout` always deny new ordinary dispatch/fulfilment before provider calls or local kitchen-order creation. Even a real approval reference does not make the ordinary endpoint a second approved-payment path. A body flag, fake approval reference, direct REST call, stale client, voucher or configuration loss cannot grant approval. The existing approved payment/completion route is the only new payment path; use durable server approval state rather than trusting the browser. Previously initiated direct payments must not be discarded, recharged or falsely called unpaid on transition: return an explicit reconciliation-required state, preserve attempts/receipts and hold any unapproved new fulfilment for named human review. No automatic refund or silent compatibility completion is authorized.
7. Keep approval separate from payment. Approval does not release the kitchen. A successful return URL, pending/authorized tender, unreadable linked Square Order or failed final authority check does not release it either. Reuse existing exactly-once claim, payment attestation, rollback/replay and immutable approved-location protections. Apply the new-fulfilment policy at every consequential browser-return, webhook, background recovery and replay boundary, with a final authoritative recheck before durable creation/release; an entry-only check is insufficient.
8. The frontend presents request submission and an explicit awaiting-review state in the new mode. The customer receives payment access only after durable approval, using the already configured gateway through the existing approved route; this slice does not switch Stripe to Square. Do not promise a response deadline, automatic approval, confirmed pickup time or SMS delivery. Use generic location-derived review copy, with the existing Revesby/morning text retained only in legacy after-hours mode. Preserve separate loading/unavailable/rejected/expired/approved/payment-pending/paid states; do not relabel a network failure as an empty queue or successful submission.
9. Preserve existing after-hours/Revesby compatibility as a separately tested mode. Existing issued vouchers remain redeemable under their existing rules; new native voucher issuance remains paused. No custom Square gift-card sale/activation is added by this slice.

## Smallest expected source scope

- `includes/class-doughboss-settings.php` and nearest existing admin settings/sanitization: explicit policy and truthful operator controls.
- `includes/class-doughboss-rest-controller.php`: availability, exact request location, ordinary bypass denial, public-safe mode configuration, approved-flow integration and independent webhook/recovery creation boundaries. In particular, `stripe_webhook()` calls `recover_stripe_order()`, which can create a paid order and send fulfilment confirmation without a browser checkout. Keep this separate from `finalize_stripe_order()`, whose existing-order replay only repairs bookkeeping. Trace any equivalent provider/background caller before accepting coverage; do not assume two endpoint gates cover every release.
- `public/js/doughboss.js` and `includes/class-doughboss-assets.php`: request-first UI, mode transitions and suppressing ordinary gateway bootstrap; preserve the immutable approved-payment page rather than adding ordinary multi-shop SDK bootstrap.
- `includes/class-doughboss-preorder-approval.php` or notification code only if direct source inspection proves a Revesby-only assumption must change; do not widen these files speculatively.
- Existing PHP, storefront and WordPress/MySQL tests nearest these contracts; no new test infrastructure.

## Acceptance before activation

- Request/approve/pay/release fixtures for each of the three supported native shops; zero payment/kitchen writes before approval; one verified release after payment; correct persisted shop throughout.
- Deny unknown, inactive, unannounced, ambiguous, pickup-disabled or remapped location; missing/wrong approver; missing approval; wrong request/cart; expired/rejected approval; direct ordinary REST bypass; master-switch or mapping drift; and final-check failure.
- Request retry and concurrent approval/completion preserve one durable request/payment/release. Full-value Card and Gift Card pass; insufficient/partial/authorized or wrongly linked tender fails without recharge or release.
- Preserve explicit legacy after-hours controls, native voucher history/redemption and direct-mode compatibility only where deliberately configured and tested.
- Failure/recovery cases for notification handoff, storage failure, timeout, browser refresh and stale frontend. No SMS success claim from configuration alone.
- Legacy ordinary attempt created under deliberate compatibility, then transition to approval-required/missing/malformed/unreadable policy, then signed paid Stripe webhook with no browser return: preserve paid evidence but create no new kitchen order, fulfilment confirmation, recharge or refund. Race browser return, webhook and replay across that transition: one durable reconciliation outcome, no unapproved release. Fail hold persistence: return retryable failure, never acknowledge successful durable handling. Already fulfilled ordinary replay may repair exact-bound bookkeeping only, with no new creation or notification. Approved-request recovery must still release exactly once after authoritative verification.
- Focused tests, PHP 7.4/8.2, Node, exact-source disposable WordPress/MySQL gate, release syntax/archive gate, inspected frozen diff and fresh independent security review. A bounded Astra assurance score of at least 8.5 is required for the frozen design and again for any substantial high-consequence implementation candidate under the owner's review requirement.
- Authenticated live acceptance, confirmed approver, seller/location ownership, real Square Web Payments/merchant/POS/KDS verification, backup/rollback proof and explicit consolidated publication approval remain separate. Unit tests, synthetic provider responses and design approval do not satisfy them.

## Decisions not granted by this design

This design does not approve online activation, universal direct checkout, Square gift-card issuance/activation, or split payment. A Square-hosted eGift purchase link may be a separate simpler sales boundary, but no seller-specific URL or ownership is configured or verified here. Preserve the owner's disabled split-checkout decision until an exclusive Square Order-writer policy exists.

## Durable transition and acknowledgement contract

The source currently permits Stripe webhook recovery to create ordinary paid fulfilment independently of browser endpoints. Approval-required policy must gate that creation path too. Inspect existing payment-attempt, event-receipt and snapshot persistence before selecting the smallest hold representation; do not introduce a new storage subsystem by assumption.

- A legacy payment with no durable fulfilled order is a paid-but-held reconciliation case, not an unpaid request and not permission to create a normal order. Persist its exact existing payment/attempt identity, receipt evidence and reconciliation hold durably and idempotently before acknowledging the event as successfully handled. Preserve its existing snapshot and financial evidence. Do not dispatch kitchen/confirmation, recharge, refund or discard it.
- If that durable hold cannot be committed, the handler must return a retryable result and retain/recover the original event/payment identity. Event acknowledgement is not proof of durable preservation; never record a success outcome first and lose the hold. Test crashes/replay at this boundary using the existing harness.
- An already durable fulfilled order is different. Exact-bound `finalize_stripe_order()` bookkeeping replay may finish without new fulfilment, provider calls or notifications, even after policy transition. Do not turn a completed historical receipt into a new approval request or block safe bookkeeping solely because the public intake mode changed.
- Existing approved-request recovery remains the only new payment-to-fulfilment path in approval-required mode. It must pass current immutable approval/payment/location checks at the actual creation/release boundary. A policy/configuration change between webhook entry and that boundary cannot grant new ordinary fulfilment.

Implementation must record a small explicit state matrix: approval required; deliberate valid legacy compatibility; missing policy (approval required); malformed/unreadable policy (new intake/payment unavailable); ordinary ordering OFF; and the separately enabled legacy after-hours exception. None of these states implicitly enables live ordering, payments, gift-card issuance or split capture.
