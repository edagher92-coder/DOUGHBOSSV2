# CRM Telegram reuse audit — 30 October 2026

## Finding

The existing Hermes business bot and its single gateway are the first integration candidate. The local Hermes project describes separate `samos` and `lifeos` profiles served by one gateway, with the business profile providing a read-only SamOS view. Reuse should preserve that gateway's ownership of Telegram updates. Neither a second polling consumer nor a new webhook registration should be attached to the existing bot as part of CRM work.

This is a source and configuration-metadata audit, not a live acceptance. Bot identity, current token ownership, active process, actual Telegram delivery mode, installed configuration precedence, current webhook, reachability and outbound delivery are **not verified**. No token, chat ID, customer data, or message content is recorded here. No Telegram API call, message, webhook change, polling session, or process operation was performed.

## Proposed reuse path

1. Keep Hermes as the sole inbound Telegram consumer. Confirm the intended business bot, profile, owner and active transport through a separately authorized, read-only operator review before selecting an integration. Do not issue `getUpdates`, register/delete a webhook, start another consumer, or reuse credentials in DoughBoss.
2. For read-only commands, evaluate a narrowly scoped DoughBoss CRM read service exposed to the existing business profile through an authenticated, allowlisted connector modeled on the SamOS boundary. Provide only the minimum fields needed, bounded result sizes and validated identifiers; treat enquiry text as untrusted data. Enforce business and user authorization in the service, return explicit unavailable/denied states, and never expose customer records to the life profile. The existing SamOS tools cannot be assumed to support DoughBoss as-is.
3. For notifications, first inspect and validate a supported Hermes-owned outbound gateway or relay interface. If one exists, DoughBoss can hand off a minimal event to that gateway over an authenticated, restricted boundary; the gateway retains Telegram credentials and recipient mapping. If no suitable interface exists, design a separately approved relay with durable queueing, deduplication and delivery/error state before implementation. Direct outbound Bot API sends do not consume inbound updates, but duplicating a bot credential expands the secret boundary and is not the preferred default. A token's existence authorizes neither sending nor changing delivery mode.
4. Validate with synthetic data locally: authorization denial, field minimization, malformed identifiers, bounded results, gateway unavailability, duplicate events and safe retry behavior. Separately approve any live configuration, recipient mapping, test message or provider action; obtain a receipt and verify the existing Hermes bot remains healthy before claiming live acceptance.

## Decisions still needed before live integration

- Verify which existing business bot/profile and recipient are authorized for DoughBoss, and determine current gateway configuration and transport without exposing secrets.
- Identify a supported outbound interface and where its credentials, queue and operator-visible delivery state live. No such interface was established by this audit.
- Agree the minimum notification content, allowed read-only commands, customer-data access rules, deployment location and failure handling. The present CRM slice does not grant messaging, customer contact, webhook changes or bot administration.
