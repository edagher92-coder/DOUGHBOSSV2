## Implemented payment safety work

The Square path now uses a versioned, stable attempt protocol:

1. An immutable keyed binding protects cart, location, fulfillment and customer/contact details without persisting raw payment tokens.
2. A named cart lock prevents concurrent provider dispatch for the same cart.
3. An attempt moves from `prepared` to `dispatching` before the provider POST. A timed-out dispatch is never silently reclaimed and reposted.
4. Bound outcomes are replayed by provider GET; unknown outcomes remain locked rather than permitting a second charge.
5. Voucher ownership is reserved and marked payment-pending before provider dispatch.
6. Only terminal failed/voided outcomes release the matching voucher reservation, under the voucher lock.
7. Paid retries restore the protected checkout snapshot and commit the order only after durable payment mapping.
8. Square webhooks remain non-fulfilling for already-paid orders; they reconcile attempt state without creating a second order.
9. A webhook that cannot durably release a voucher is marked retryable and returns HTTP 500 instead of acknowledging incomplete recovery.
10. Legacy attempts drain fail-closed, including nullable metadata and datasets where the first 100 rows are already fulfilled.
11. Reconciliation is sticky for mismatched or stale provider outcomes and validates currency, mode and location drift.
12. Unresolved-payment snapshots are protected from ordinary expiry and purge.
13. The browser clears pending state only for an explicit retry-safe outcome.

The contained design intentionally does not auto-create orders from payment webhooks or switch POS ownership. Automated fulfillment, refunds, kitchen printing and provider-specific KDS routing remain a separate operational project.

## Multi-site and SamOS direction

GitHub discovery identified `snowflow-ask-sam` as the SamOS repository. Its existing DoughBoss contracts use the correct hierarchy:

```text
DoughBoss business workspace
└── WordPress installation/site identity
    └── authorized location identity
        └── source-receipted status, menu and operations views
```

Never treat a bare numeric location ID as globally unique. The eventual adapter must bind an owner-approved installation ID and source origin, store credentials server-side, enforce workspace/site/location grants, and expose observed-at/source-revision/freshness states. The current work does not claim a live SamOS ↔ DoughBoss connection.

## Competitor and POS benchmark

The storefront direction was checked against public Crust, Manoosh & Co and Domino’s ordering surfaces. The resulting DoughBoss design emphasizes a faster mobile customizer, persistent cart state, location clarity, food-first imagery and accessible motion rather than copying another brand. Public-page comparisons are qualitative; no competitor conversion metric or private checkout was available.

For an all-in-one pizza/restaurant pilot, Square for Restaurants remains the leading practical candidate because payments, restaurant POS and kitchen workflows can be evaluated together. Stripe is a strong payment platform, but Stripe Terminal alone is not a full restaurant operating system. Lightspeed Restaurant is the stronger multi-location benchmark; SumUp’s reviewed Australian offer did not establish equivalent modifier/KDS/multi-site depth. This is a pilot recommendation, not purchase or migration approval.

Square web payments and Square POS/KDS are distinct integrations. Prove catalog/modifier mapping, receipts, refunds, kitchen routing, offline behavior and multi-location reporting at one shop before replacing POSPal or enabling a second fulfillment path.
