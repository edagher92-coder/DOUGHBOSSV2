## Implemented payment safety work

The Square path now uses a versioned, stable attempt protocol:

1. An immutable keyed binding protects cart, location, fulfillment and customer/contact details without persisting raw payment tokens.
2. A named cart lock prevents concurrent provider dispatch for the same cart.
3. An attempt moves from `prepared` to `dispatching` before the provider POST. A timed-out dispatch is never silently reclaimed and reposted.
4. Bound outcomes are replayed by provider GET; unknown outcomes remain locked rather than permitting a second charge.
5. Voucher ownership is reserved and marked payment-pending before provider dispatch.
6. Only terminal failed/voided outcomes release the matching voucher reservation, under the voucher lock.
7. Paid retries restore the protected checkout snapshot and commit the order only after durable payment mapping.
8. Square webhooks remain non-fulfilling for already-paid orders; they reconcile attempt state without creating a second order.
9. A webhook that cannot durably release a voucher is marked retryable and returns HTTP 500 instead of acknowledging incomplete recovery.
10. Legacy attempts drain fail-closed, including nullable metadata and datasets where the first 100 rows are already fulfilled.
11. Reconciliation is sticky for mismatched or stale provider outcomes and validates currency, mode and location drift.
12. Unresolved-payment snapshots are protected from ordinary expiry and purge.
13. The browser clears pending state only for an explicit retry-safe outcome.

The contained design intentionally does not auto-create orders from payment webhooks or switch POS ownership. Automated fulfillment, refunds, kitchen printing and provider-specific KDS routing remain a separate operational project.

### Reproduced defects and bounded repair

The existing disposable WordPress/MySQL harness was extended rather than replaced. Against unmodified runtime code, 190 assertions produced 185 passes and exactly five failures: three showed that a normal paid Stripe checkout left its snapshot prepared and payment attempt unverified/unlinked; two showed that changed post-payment contact facts could create a paid order. These are demonstrated local defects, not a diagnosis that they caused the owner's live Stripe outage.

The controller now verifies hosted Stripe returns against the immutable snapshot's name, email, phone, address and notes, as well as the existing payment/cart/money/context bindings. Contact drift returns `doughboss_pay_attempt_changed` / HTTP 409; a missing or misbound snapshot fails closed. No Stripe checkout-key, Session/PaymentIntent identity, provider request format, database schema or Square protocol is changed. Ordinary Stripe snapshot expiry remains in force; Square's retention exception is not broadened.

One shared finalizer links the verified durable order to its snapshot and payment attempt, checks both writes by their returned/read-back state, and reports `doughboss_pay_finalize_pending` / HTTP 503 if bookkeeping remains incomplete. Normal browser checkout, session-backed browser replay and signed webhook recovery use it. A valid Stripe return is rate-limited and verified before generic cached/durable browser exits, so a cached response cannot hide incomplete linkage. Browser-origin and webhook-origin order keys retain their existing distinct identities.

Only a newly created order attempts a confirmation, before a fallible finalization return. A retry repairs records without another order, provider creation request or confirmation attempt. This does **not** promise exactly-once real mail delivery: process loss between order commit and notification, and an ambiguous mail transport outcome, remain pre-existing limitations requiring a separate notification/outbox design. No such infrastructure was added. Verified replay depends on provider GET availability and an unexpired snapshot; no offline-success or extended-retention claim is made.

The existing PowerShell integration runner now defines `WP_HTTP_BLOCK_EXTERNAL` before WordPress loads in both its primary and concurrent workers. The harness refuses to run without that block and its exact disposable-site/database guards. Synthetic Stripe interception allows only hosted Session creation and Session/PaymentIntent retrieval; no live credentials, customer data, provider request or mail transport is used. The locations reset is confined to this guarded disposable database and preserves the original fresh-seed and reactivation assertions.
